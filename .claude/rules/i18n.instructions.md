# Internationalisation (i18n)

## Frontend

- Every user-visible string goes through vue-i18n (`frontend/src/locales/`). No raw text in templates.
- Keys are named by feature/epic (e.g. `ag.resolution.title`), never source text as key.
- Generic labels (actions, field labels, common statuses) always reuse the existing `common.*` key — the same text must never be redefined under another key. Exception: dynamic enum namespaces (e.g. `tasks.statuses.*`, `contracts.statuses.*`).
- `common.*` is reserved for **general semantics only**: field labels (`title`, `description`, `address`…), generic CRUD actions (`save`, `cancel`, `delete`…), generic states (`pending`, `overdue`…), transverse empty/error states. A key whose semantics belong to a single feature/page **must stay in its own namespace** (e.g. `nav.dashboard`, `budget.closeExercise`, `auth.newPassword`) — except if its text duplicates a `common.*` value.
- Filter "all" labels follow the same rule: `Tous les X` filter options reuse `common.all*` keys — never create per-feature duplicates like `tasks.allPriorities` / `tasks.allAssignees`.

### Classification at creation time (ordinary vocabulary → `common.*` by default)

When adding a **new** key, classify by the *text*, not by the feature it appears in: if the value is ordinary vocabulary — a field label (`title`, `priority`, `contractor`…), a generic action (`save`, `loadMore`…), a generic state (`pending`, `overdue`…), a generic filter/search word (`all`, `search`, `filter`…) — the key **must be created directly under `common.*`**, even if it is used by a single feature on a single page. A feature namespace is only for text whose meaning belongs to that feature (`nav.dashboard`, `budget.closeExercise`, `tasks.vendorTokenActive`…). "Common" means ordinary language, not "used by N features": a word any user of any page could meet belongs in `common.*` from the start.

### Anti-duplicate procedure (text wins over semantics)

**Duplication is decided by value, not by key**: a feature-namespaced key whose text is byte-identical to an existing `common.*` value is a duplicate and must be removed — point the usage at the `common.*` key instead.

Concretely, before adding or keeping a key outside `common.*`:

1. Is the text ordinary vocabulary? → create/reuse it under `common.*` (see above).
2. Search the locale file for the exact string: if it already exists under `common.*`, reuse that key and delete the duplicate.
3. If it exists under another feature namespace with the same text, promote the shared text to `common.*` (new key if none fits) and update all usages.
4. Only dynamic enum namespaces (`*.statuses.*`, `*.priorities.*`, filter-tab labels tied to an enum value…) may keep feature-local values.

Check for duplicates mechanically when touching locales, e.g. a one-liner that lists every non-`common` value that also exists under `common.*`.

## Backend

- The backend never returns a displayable hard-coded error message: it returns stable error codes under the `errors.*` namespace, translated on the frontend via vue-i18n.
- Any new error code must have a translation in every locale.

## Local formats

- Dates, numbers and amounts are formatted with `Intl` using the `fr-FR` locale by default (the application is French).
- Amounts are stored as integer cents in the backend, formatted on the frontend.
